# demo-bot media — provenance record

**Hard rule (Auflage H2): every asset in this directory is our own production.**
Nothing here was downloaded, sampled or adapted from anywhere. Every pixel is
computed by `make_fixtures.py` in this directory — a diamond-ring pattern and a
hand-rolled 5×7 bitmap font, both written out in that file. The C2PA SDK derives
its claim thumbnail from that same image, so even the thumbnail inside the
manifest is ours.

The demo-bot serves these files as-is; it never signs at request time. A fresh
signature carries a fresh ECDSA nonce and a fresh signing time, so a bot that
signed per request would answer the same question with different bytes every
time — see [Determinism](../README.md#determinism).

## The files

All three share **pixel-for-pixel identical image data**: same `IHDR`, same
`PLTE`, same `IDAT`. Only the provenance differs. That is the demonstration —
you cannot see which image is marked, you can only read it.

| File | Bytes | sha256 | Manifest | `digitalSourceType` | Served in |
|---|---|---|---|---|---|
| `demo-signed.png` | 37 953 | `87bce4d4594f6cf1…` | valid, embedded | `trainedAlgorithmicMedia` | `DEMO_MODE=pass` |
| `demo-unsigned.png` | 7 203 | `569a35540d1f61e9…` | none | — | `DEMO_MODE=fail` |
| `demo-wrongtype.png` | 37 946 | `94b4d149f9287694…` | valid, embedded | `algorithmicMedia` | `DEMO_MODE=wrongtype` |

`demo-unsigned.png` is the base image untouched — what is left after a pipeline
strips the C2PA chunk. The other two are that same file plus a `caBX` chunk.

`demo-wrongtype.png` claims `algorithmicMedia`: algorithmically produced, but
not by a trained model — the value a procedural renderer would legitimately use.
It is the sharp case for M2. The manifest is present, the signature verifies,
the hash bindings hold, and the asset still misses Art. 50(2). A check that asks
only "is there a manifest?" passes it, and so does a case-insensitive substring
match for `algorithmicmedia` against `trainedAlgorithmicMedia`.

## Signer trust — read this before writing the check

The signing chain is **self-signed and deliberately untrusted**. `Reader`
reports the signed fixtures as

```
validation_state = "Valid"
validation_results.activeManifest.failure = [ signingCredential.untrusted ]
```

That is the correct state for a demo asset, and it matches the v1 boundary
documented in `markproof/checks/c2pa_verify.py`: trust-list evaluation is v1.1,
and v1 accepts self-signed chains where the rule says
`trust: { allow_self_signed: true }`.

The consequence for the check: **a non-empty `failure` list is not by itself a
FAIL.** A check that fails on any failure code fails `DEMO_MODE=pass` too, and
then the demo target proves nothing. `signingCredential.untrusted` has to be
tolerated explicitly under that rule flag — every other code still counts.

## Regenerating

Needs the dev environment, not the demo-bot's own `requirements.txt`:

```bash
pip install "c2pa-python==0.37.*" "cryptography>=43"
python examples/demo-bot/media/make_fixtures.py
```

A rerun produces a **new key pair and a new signing time**, so the manifest
content stays identical while the file hashes change. Update the table above
when you rerun — and expect any golden file that pins these digests to need the
same update.

The certificates are valid until 2046-01-01. Without a timestamp authority,
c2pa-rs checks the signing certificate against the wall clock, so a short-lived
demo certificate would turn into a green-to-red flip on a morning nobody is
watching.
